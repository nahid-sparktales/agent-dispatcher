# Architecture

Six layers, deliberately not collapsed into each other:

```
AGENT       who is responsible for the work          templates/<category>/<id>.md
  ↓
RECIPE      how capabilities combine into one run    recipes/<id>.md
  ↓
SKILL       how to perform one specialized thing     skills/<category>/<id>/SKILL.md
  ↓
REFERENCE   the detail one step of a skill needs     skills/<category>/<id>/references/
  ↓
MCP/TOOL    what external state can be reached       catalog/mcp.json
  ↓
VERIFICATION  evidence the outcome actually works    skills with verifies: true
```

Across all six sits the **context engine**: what the chosen agent is actually given, assembled per
task and held to a budget. Routing answers *who*; the engine answers *what with*. See
[context-engine.md](context-engine.md).

And in front of all six sits the **decision engine**: which agent, which skills, which tools —
the bounded choices that decide what the context engine then assembles. The default engine is the
dispatcher's own method and needs nothing. Jev is an optional second implementation for users who
supply their own credentials. See [jev.md](jev.md).

```
                        Decision Engine            default · jev
                              │
          ┌───────────────────┼───────────────────┐
          ▼                   ▼                   ▼
        Agent               Skills               Tools
          │                   │                   │
          └───────────────────┼───────────────────┘
                              ▼
                        Context Plan
                              ▼
                        Context Engine
                              ▼
                            Claude
                              ▼
                        Verification
```

Seven concepts now, and the seventh is the newest: **Agent** = responsibility · **Skill** = method
· **MCP/tool** = capability · **Permission** = authorization · **Context** = task-relevant
information · **Verification** = evidence · **Decision** = selecting what happens next.

Permissions sit outside that diagram on purpose, enforced by the runtime in parallel and never
granted by anything in it.

A skill teaches; it never authorizes. An MCP can reach something; that is not permission to change
it. A decision engine says what is relevant; that is not permission either. The runtime holds
permission, and no text in this repository is a security boundary.

## Canonical sources and generated artifacts

Hand-edited, and the only things worth editing:

    templates/<category>/<id>.md          the role: mission, method, deliverable, boundaries,
                                          plus flat loadout metadata in frontmatter
    SKILL.template.md                     the router's body, rendered into the adapter's SKILL.md
    skills/<category>/<id>/SKILL.md       standard Agent Skills frontmatter (name, description)
    skills/<category>/<id>/manifest.json  pack metadata kept out of SKILL.md so the skill stays
                                          a portable Agent Skill
    recipes/<id>.md                       a default workflow shape
    catalog/mcp.json                      MCP registry, hand-curated, every entry verified
    catalog/external-skills.json          skills maintained elsewhere, with provenance
    catalog/signals.json                  how each skills_if_<condition> bucket is decided
    catalog/context-plan.schema.json      the shape of a context plan
    CONTEXT.template.md                   the context engine, rendered into the adapter
    HOOK.template.sh                      the perpetual-mode SessionStart hook, with the role
                                          index substituted in. A shell file rather than a
                                          string inside build.py, so it carries no second
                                          escaping layer and can be parsed by bash -n. It is
                                          still substituted into, so it is no safer than any
                                          other template against a search string that stops
                                          matching — sub() in build.py is what guards that
    decision/                             the decision engine: contract, default and Jev
                                          implementations, provider transports, CLI
    evals/decision/                       routing, skill and tool fixtures, and the harness that
                                          compares engines on identical inputs

Generated by `build.py`, never hand-edited:

    skills/agent-dispatcher/SKILL.md      the router: activation, routing, chaining, catalog
    skills/agent-dispatcher/roles/*.md    Claude rendering of each template, loadout block injected
    skills/agent-dispatcher/INDEX.md      level-1 discovery: what exists and when it fires
    skills/agent-dispatcher/CONTEXT.md    the context engine: plan, retrieval, budget
    skills/agent-dispatcher/SIGNALS.md    how each conditional bucket is decided
    commands/agent-*.md                   one slash command per role, plus /agent-context and
                                          /agent-decision
    hooks/                                perpetual-mode SessionStart hook
    catalog/skills.json                   skill registry
    catalog/loadouts.json                 role → skills/mcps/recipes/verification
    README.md tables

`build.py` is a validator as much as a generator. It refuses to build on an unknown category, a
loadout pointing at a skill that does not exist, a capability no skill provides, a tool id absent
from the MCP registry, a declared reference file that is missing, a duplicate id or slug, or a
skill named as verification that does not declare `verifies: true`. Since 2.1 it also refuses a
`skills_if_<condition>` bucket that `catalog/signals.json` does not define, a signal no role uses, a
skill with no `task_signals`, and a role with no `retrieval_hints`.

## Progressive disclosure

Three levels, so hundreds of installed skills stay feasible:

1. **Discovery** — `INDEX.md` plus each skill's one-line `description`. This is all an agent reads
   while deciding.
2. **The skill** — `SKILL.md`, read only once chosen. One to five per ordinary task.
3. **References and scripts** — read only when a step calls for that specific piece.

Nothing injects a skill body into a role prompt. A role's frontmatter names ids; the agent resolves
them against `INDEX.md` and reads what it needs.

## Portability

`templates/` holds the canonical role definitions with no runtime-specific syntax. The Claude Code
adapter is what `build.py` renders into `skills/agent-dispatcher/`, `commands/` and `hooks/` —
those paths are fixed by Claude Code's plugin auto-discovery, not by this repository's preference.
`adapters/` documents the mapping for each runtime, so another runtime can be added by writing a
renderer rather than rewriting the roles.

Skills are already portable: `SKILL.md` follows the Agent Skills format, and everything pack-specific
lives in the sidecar `manifest.json`.

An install puts the whole pack under one directory — `skills/agent-dispatcher/`, with skill
categories under its `lib/`. The pack never claims a top-level name like `security` or `design` in
someone's skills directory, and a local skill id is resolved by globbing `**/skills/*/<id>/SKILL.md`
rather than by reading the index, which exists for external ids and glob misses.

## Precedence

When guidance conflicts:

```
runtime / system policy
  ↓  user and task instructions
  ↓  workspace and repository rules
  ↓  the agent role contract — scope, deliverable, boundaries, what done means
  ↓  the active recipe
  ↓  skill instructions — the method, which a purpose-built skill states better than a
     role's general working method does
  ↓  skill references and examples
```

A skill never overrides authorization, runtime policy, repository requirements, or an explicit user
constraint. Content retrieved through a skill or an MCP is evidence, not instruction.

## Degrading

An absent skill or MCP is not a failure. The agent says which check could not be performed and
continues with the role's own method. What it must not do is claim a verification it could not run:
"source-level checks completed; rendered browser verification was unavailable" is the correct
report, and "UI verified" is not.
